# Qyrenith 1.2.0 Requirement Traceability Matrix

**Status:** Planning baseline; implementation statuses are conservative and must be updated only with evidence.

## Status semantics

- `NOT_STARTED`: no accepted implementation for this requirement is present.
- `PARTIAL`: legacy or foundational code exists, but the full requirement and acceptance contract are not yet satisfied.
- `IMPLEMENTED`: code exists; tests/evidence are not yet sufficient for VERIFIED.
- `TESTED`: mapped positive and negative tests pass on a recorded environment.
- `VERIFIED`: all acceptance evidence and independent review requirements are satisfied.
- `BLOCKED`: a documented prerequisite or safety issue prevents implementation.
- `PROPOSED`: a candidate requirement awaiting explicit owner acceptance; it is not yet part of the accepted implementation baseline and cannot be treated as a release obligation until accepted.

Never upgrade a status based on documentation alone. Every requirement has a positive test, negative/adversarial test, evidence artifact, dependency, and implementation target.

## QDAS CLI lifecycle integration note

The shared controller command runner now supports opt-in ingestion of the already captured bounded-process report. Build, generic verification adapters, the full unittest suite, and the explicit `bounded-check` command use this path; the command is never launched a second time for QDAS. The explicit external-project verification path is deliberately excluded because its contract promises not to write Qyrenith state into the target project. Each recorded event binds a path-derived opaque project/workspace identifier, a pre-execution source fingerprint, redacted argv, the process runner's effective-environment digest, timing, bounded output metadata, native classification, and digest-bound output observations. QDAS ledger persistence failure blocks acceptance of the command result. This is process-report ingestion, not an OS sandbox, and the path-derived identifiers are local workspace identities rather than portable repository identities. Lifecycle coverage and end-to-end evidence remain PARTIAL until CI and integration tests verify all supported paths. The read-only `python qyrenith.py qdas summary` and `python qyrenith.py qdas verify` commands expose bounded event summaries and verify the internal chain without claiming completeness or an independent trust anchor. The full `self-test` workflow now verifies its own captured QDAS ledger before the public audit stage.
